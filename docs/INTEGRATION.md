# 接口与生命周期

## 游戏提供什么

每个人机使用一个 `BotController`。库读取状态并返回控制命令，接入的游戏负责感知、敌我判断、导航、碰撞、目标点、后坐模型、镜态、武器发射和伤害。文档中把接入的游戏称为宿主。

默认使用游戏原有的瞄准，配置为 `aim.authority:'host'`。也可以改用 `library` 瞄准，再按需要组合狙击或射后移动。

接口使用米、米／秒、秒、弧度和弧度／秒。右手坐标为 X 前、Y 左、Z 上，yaw 向左为正，pitch 向上为正。游戏使用其他坐标或单位时，在适配器里转换，参见 [adapters.cjs](../examples/adapters.cjs)。

`Identity` 包含 `world`、`entity`、`life` 和 `weapon`。换世界、复活、换枪，或者对象编号重新分配时，要更新对应标识。

`Evidence` 包含状态值 `value`、采样时间 `sampledAt` 和有效期 `validUntil`。时间使用同一个持续前进的控制时钟，更新序列递增。部署期间即使暂停了比赛，控制时钟和部署更新也要继续走，否则超时检查会跟着停住。

## 一次更新怎么执行

1. 采样身份、存活、武器状态、弹药、任务和导航优先级、运动状态及当前目标。眼部视线和枪口视线分别提供。
2. 将自动武器等允许延后交付的执行结果放进 `frame.receipts`，调用 `update`，得到只读的 `Decision`。
3. 核对命令的身份、顺序和期限，再执行 `actions`。重复的 `hold` 保持扳机状态，保留游戏原有的冷却和弹药周期。
4. 每次实际出弹前，先检查游戏自己的武器条件，再采样 `liveFrame` 并调用 `beforeDischarge`。它会重查当前许可、身份、模式、目标和 focus、敌我、视线、运动及实际瞄准。
5. 请求被接受时报 `accepted`，实际出弹后才报 `shot`。狙击必须同步调用 `recordShot`，在下一次 `beforeDischarge` 或 `update` 之前交付。自动武器可以在下一帧按实际发生时间回传。事件 ID 对应唯一的真实事件，`actualShots` 填实际发射数。
6. 退出时先执行 `reset` 返回的清理命令，再销毁游戏实体。清理按原身份执行，尤其要核对已经复用的对象编号。

`beforeDischarge` 只检查许可，不预留一发。狙击的单发许可在收到同步出弹结果后失效，因此异步批量交付狙击 `shot` 不在支持的调用顺序内。武器发射失败时不记 `shot`，继续遵守游戏自己的武器条件。

## 命令和回执

回执是游戏实际执行命令后的结果。

| 命令 | 执行及反馈 |
| --- | --- |
| hold | 保持本库的扳机状态，请求结果与实际 shot 分开回报 |
| release | 松开本库持有的扳机，完成后报 stopped |
| delegate | 清理本库的瞄准和移动输入，归还游戏原有控制器 |
| aim | 按最大角速度驱动输入视角，保留游戏后坐和散布 |
| move | 执行指定的可达候选，实际开始和结束时报 motion-started／motion-ended |
| brake | 调用游戏的地面刹停方法，下一帧反馈真实速度 |
| scope-enter／scope-release | 改变本库请求的镜态，下一帧反馈真实 scope |

回执带上 `commandId`、原 `Identity` 和实际发生时间 `time`。移动回执还会核对当前组。开始回执晚到时，库先按真实开始时间检查排队期限，再按当前时间决定是否刹停。`stopped` 只确认当前停止操作中的命令，旧组结果会与新组分开处理。

同一个 `hold` 可以持续多个采样周期，其出弹结果按更新后的组许可检查，较长的重试间隔也能正常计数。库保留最近 512 条事件用于去重，命令和授权记录各保留 256 条。超出记录窗口的迟到回执会忽略，长期统计请在游戏侧保存。

## 中断、瞄准和移动

状态过期、目标变化、切换模式、遮挡、失敌或游戏任务优先时，库会撤销开火许可。同一把武器换目标或模式时，保留已有的恢复期限；世界、生命或武器身份变化时，清理旧状态。

短暂的跟踪等待会保留已经开始的窗口时钟，等待过程不延长窗口。即使主循环停顿，出弹回调仍要检查许可期限，及时停止开火。

`host` 瞄准由游戏提供 `target.aligned`。使用 `library` 瞄准时，还要提供目标位置、速度、半径、`inputView`、转换后的 `recoilOffset` 和真实 `effectiveView`。库会在出弹前复查枪线和散布。有限预判用来补偿跟踪延迟，弹丸飞行的解算由游戏处理。

库瞄准可以与 `sniper` 一起使用。这时狙击按实际枪口对准情况判断就绪，不额外依赖游戏侧的 `aligned`。

射后移动需要带有效期的可达、无遮挡候选，以及真实执行回执。`move.validUntil` 取排队上限和两条路径证据期限的最早值，游戏在执行前核对它。移动开始后的路径变化和碰撞继续由游戏导航处理。

导航、特殊任务和已经开始的威胁规避优先，`threatEvasionActive` 表示规避实际开始。移动距离和停稳阈值按游戏尺度配置。狙击还需要真实的 `scope`、`stationarySpread` 和开镜等待时间，库只清理自己请求的镜态。

## 名单、部署和聊天

`createRoster` 按玩家的相对关系生成 `ally` 和 `enemy`，具体阵营由游戏映射，人数上限包含人类玩家。计划中的 `ready` 为 false，实际就绪由执行回执确认。

`LoadoutPlanner` 接收通用字符串 ID 和完整的 `slots`，游戏通过 `admits` 判断装备是否可用。同一人机在同一回合的选择保持稳定，可以用 `snapshot` 和 `restore` 保存、恢复。落盘、版本迁移和并发处理留给游戏，比赛结束后调用 `clear`。

`DeploymentControl` 默认每次发出一个创建请求。`freeze` 要覆盖游戏输入和比赛时钟，实体、装备、武器全部实际就绪后才报 `ready`、解除冻结。创建请求被接受只代表开始处理。失败或超时后，游戏执行返回的 `remove` 和 `unfreeze`；再次 `begin` 前先 `cancel`。

`DialogueControl` 使用游戏传入的内容、事件和频道。先 `peek`，确认消息显示成功后再 `commit`。开局按顺序发送，每场一次，同一人可以连续发言。新回合 `offer` 会先清理旧队列，忽略倒退的回合事件；冷却跨回合保持。退出时 `clear`，或初始化新比赛。

字段和默认值见 [PARAMETERS.md](PARAMETERS.md)，完整类型见 [index.d.ts](../src/index.d.ts)。本版记录的是离线测试结果，实际运行耗时需要在接入的引擎里测量。
